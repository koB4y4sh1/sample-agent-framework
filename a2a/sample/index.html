client と agent の通信の流れ

client はまず Agent Card を読み、次に Message を Task として送ります。 agent は Task の状態や成果物をイベントとして返します。下の図は、実際に どのリクエストがどちら向きに流れるか を示しています。

1.2Agent Card を取得 A2ACardResolver が接続先の情報を読みます。
GET → ← JSON /.well-known/agent-card.json
能力を公開 capabilities / skills / supported_interfaces を返します。
1.3Message を送信 SendMessageRequest(message=message) を作ります。
send_message → message_id / context_id / parts を送る
Task を開始 Task(id, context_id, SUBMITTED) を最初のイベントとして返します。
1.4完了結果を受信 短い処理では最終 Task 内の artifacts を読みます。
← Task COMPLETED + artifacts
同期的に完了 add_artifact() の後に complete() します。
1.5 / 1.6イベントを順番に読む async for で status_update / artifact_update を受け取ります。
← ← ← stream WORKING、artifact chunk、COMPLETED
途中経過を送る update_status() や add_artifact(append=True) を複数回呼びます。
1.7Task 状態を再取得 受け取った task_id を GetTaskRequest に入れます。
get_task → ← Task 現在の status を問い合わせる
保存済み Task を返す InMemoryTaskStore にある現在状態を返します。
1.8キャンセル要求 CancelTaskRequest(id=task_id) を送ります。
cancel_task → ← Task CANCELED を受け取る
cancel() を実行 実行中リストから外し、TaskUpdater.cancel() で終了します。
1.9同じ context_id で再送信 task_id は毎回別でも、context_id を同じにします。
send_message → ← Task 同じ会話として関連付ける
context_id ごとに処理 このサンプルでは context_id 別の turn 数をメモリで数えます。
1.10失敗状態を受信 status_update の state と message を表示します。
← status_update REJECTED または FAILED
reject / failed を返す 入力不備は reject、処理中の失敗は failed で返します。
読む順番: Agent Card で接続先を知る → send_message で Task を作る → Task/status/artifact のイベントを読む → 必要なら get_task / cancel_task / 同じ context_id で追加送信する、という流れです。

各章が通信のどこに当たるか

通信の役割で見ると、どの章が「確認」「送信」「返答」「運用操作」なのかがすぐ分かります。

1.2 接続前の確認 client が agent の能力を確認してから会話を始めます。
1.3 依頼の送信 client から agent へ Task を送る基本通信です。
1.4 〜 1.6 返答の種類 agent がどう返すかを、即時・分割・進捗通知で比べます。
1.7 〜 1.10 運用時のやり取り 状態確認・キャンセル・継続会話・エラー応答を扱います。
重要な区別 message は依頼内容、Task は処理単位、artifact は最終成果物、status_update は進捗や失敗通知です。
