Compaction を
「会話履歴の整理術」として理解する

Compaction は、長くなった会話をそのまま捨てる機能ではありません。モデルに渡す情報量を抑えながら、必要な文脈を残すための段階的な圧縮設計です。

最初に伝えるべき結論

Agent Framework の Compaction は、古い履歴を「短くする・要約する・最後に削る」ための仕組みです。おすすめは、まずツール結果を軽くし、次に古い会話を要約し、それでも大きい場合だけ最新履歴に絞る順番です。

1. なぜ Compaction が必要なのか

Agent は、毎回「最新の質問だけ」をモデルに渡すわけではありません。実際には、システム指示、会話履歴、ツール定義、ツール結果、今回の入力などをまとめて渡します。会話が長くなるほど、この入力が肥大化します。

🚧 上限に当たる

モデルには一度に読める量の上限があります。履歴が大きすぎると、処理できなくなります。

💰 コストが増える

毎回すべての履歴を送ると、入力トークンが増え、API費用が膨らみます。

🐢 遅くなる

読む情報が多いほど、モデル応答までの待ち時間が増えやすくなります。

🎯 重要情報が埋もれる

古い話題や巨大なツール結果が残ると、今の質問に不要な情報がノイズになります。

圧縮なし / 圧縮ありの違い

圧縮しない場合
古い会話
過去の相談が全文で残る
ツール結果
検索結果やAPI応答が長いまま残る
現在
入力上限・コスト・遅延の問題が起きる
履歴サイズ 92%
圧縮する場合
古い会話
要点だけに要約する
ツール結果
古い結果を短い説明に折りたたむ
現在

履歴サイズ 48%

2. Compaction が効く対象 / 効かない対象

重要: メモリ内履歴を自前管理する Agent 向け

Compaction は、Agent が自分でメモリ内のメッセージリストを保持し、各呼び出しで完全な履歴をモデルへ渡す場合に効果があります。

✅ 効果がある

  • InMemoryHistoryProvider などで履歴を持つ Agent
  • ツール結果や検索結果を会話履歴に残す Agent
  • 長期対話・調査・サポート用途の Agent

⚠️ 効果が薄い / ない

  • Foundry Agents のようにサービス側がコンテキストを管理する場合
  • Responses API の store 有効時など、会話状態をサービス側が管理する場合
  • Copilot Studio のように会話コンテキストをサービス側が維持する場合
Python 版の注意

Compaction Framework は Python では試験段階です。戦略は agent_framework._compaction から import します。実運用では、バージョン変更に備えてラップ層を置く設計が安全です。

3. 重要概念: MessageGroup / Trigger / Target

📦MessageGroup

メッセージを安全に扱うためのまとまり。ツール呼び出しとツール結果は片方だけ消すと壊れるため、1グループとして扱います。

→
🔔Trigger

いつ圧縮を開始するか。例: トークン数がしきい値を超えた、メッセージ数が多い、ツール呼び出しがある。

→
🎯Target

どこまで圧縮したら止めるか。目標を満たしたら、それ以上は削りません。

MessageGroup の種類

種類 意味 圧縮時の扱い
system システムメッセージ 常に保護する
user ユーザーの発話 古いものは要約・削除対象になり得る
assistant_text 通常のAI応答 古いものは要約・削除対象になり得る
tool_call ツール呼び出しとツール結果 必ずまとまりとして扱う。片方だけ消さない
summary 要約戦略で生成された要約 古い会話の代替文脈として残す

4. 圧縮戦略の選び方

戦略は「弱い圧縮」から「強い圧縮」へ順に使うのが基本です。最初から削除に頼ると、必要な文脈まで失いやすくなります。

おすすめの順序

🧰1. ツール結果を軽くする

ToolResultCompactionStrategy
古いツール結果を短い要約メッセージに折りたたむ。

→
📝2. 古い会話を要約する

SummarizationStrategy
重要な事実・決定・ユーザー設定を残す。

→
🪟3. 最新履歴に絞る

SlidingWindowStrategy / TruncationStrategy
最後の防衛策として古いグループを除外する。

戦略 強さ 何をするか LLM要否 向いている用途
ToolResultCompactionStrategy 低 古いツール結果を短い要約メッセージにする 不要 検索・API・ファイル読み取りが多いAgent
SelectiveToolCallCompactionStrategy 低〜中 古いツール呼び出しグループを完全に除外する 不要 古いツール履歴が不要な場合
SummarizationStrategy 中 古い会話をLLMで要約し、要約メッセージに置き換える 必要 長期対話・サポート・相談
SlidingWindowStrategy 高 最新の一定グループだけ残す 不要 単発依頼、軽量処理、厳格な履歴制限
TruncationStrategy 高 古いグループを削って指定サイズに近づける 不要 緊急のトークン予算バックストップ
TokenBudgetComposedStrategy 設定次第 複数戦略を順番に実行し、予算達成で停止する 戦略次第 実運用の標準構成

5. 実装パターン

Python での基本構成

from agent_framework import Agent, CompactionProvider, InMemoryHistoryProvider
from agent_framework._compaction import (
    CharacterEstimatorTokenizer,
    SlidingWindowStrategy,
    SummarizationStrategy,
    TokenBudgetComposedStrategy,
    ToolResultCompactionStrategy,
)

tokenizer = CharacterEstimatorTokenizer()

pipeline = TokenBudgetComposedStrategy(
    token_budget=16_000,
    tokenizer=tokenizer,
    strategies=[
        ToolResultCompactionStrategy(keep_last_tool_call_groups=1),
        SummarizationStrategy(client=summarizer_client, target_count=4, threshold=2),
        SlidingWindowStrategy(keep_last_groups=20),
    ],
)

history = InMemoryHistoryProvider()
compaction = CompactionProvider(
    before_strategy=pipeline,
    history_source_id=history.source_id,
)

agent = Agent(
    client=client,
    name="ShoppingAssistant",
    instructions="You are a helpful shopping assistant.",
    context_providers=[history, compaction],
)

ポイントは、履歴プロバイダーと compaction provider を同じ context_providers に登録し、history_source_id で圧縮対象の履歴を指定することです。

before_strategy / after_strategy / ad-hoc の違い

種類 タイミング 目的 使いどころ
before_strategy モデル呼び出し前 今回モデルへ渡す文脈を小さくする 通常のメイン構成
after_strategy モデル応答後 保存済み履歴を次回に備えて軽くする ツール結果などを永続的に軽くしたい場合
apply_compaction 任意 セッション外の message 配列を直接圧縮する バッチ処理・移行・検証用
要約用モデルは別に考える

SummarizationStrategy は要約用のLLMクライアントが必要です。公式では、品質を保ちつつコストを下げるため、小さく安価なモデルを使うヒントが示されています。

6. 実運用での設計判断

1
まず残す情報を決める

最新のユーザー依頼、直近の応答、直近のツール結果、システム指示は優先して残します。

2
ツール結果から軽くする

検索結果・API応答・ファイル読み取り結果は肥大化しやすいため、最初の圧縮対象にします。

3
意味が必要なら要約する

古い相談内容や決定事項を残したい場合は、削除ではなく要約を使います。

4
削除は最後の手段にする

Sliding Window や Truncation は強力ですが、文脈を失います。バックストップとして扱います。

ユースケース別のおすすめ

ユースケース おすすめ構成 理由
社内文書検索Agent ToolResult → Summarization → SlidingWindow 検索結果が大きく、過去の質問意図も残したい
FAQ回答Agent ToolResult → SlidingWindow 長期文脈より、軽さと安定性が重要
業務相談Agent Summarization中心 過去の決定事項やユーザー事情が重要
コード調査Agent ToolResult → Summarization → Truncation ファイル内容・検索結果が肥大化しやすく、最後の予算制御が必要
バッドプラクティス
  • 最初から TruncationStrategy だけに頼る
  • 要約を原文の完全な監査証跡として扱う
  • token_budget をモデルの上限ぎりぎりにする
  • ツール呼び出しとツール結果を別々に削除する
おすすめ初期値の考え方

明確な根拠がない初期段階では、TokenBudgetComposedStrategy に ToolResultCompactionStrategy、SummarizationStrategy、SlidingWindowStrategy を順に入れる構成が分かりやすいです。強い削除戦略は最後に置きます。

まとめ

Compaction の本質は、履歴を雑に削ることではありません。「残す」「軽くする」「最後に捨てる」順番を設計することです。

非エンジニア向けには、Agent が会話を続けるための「整理整頓」と説明すると伝わりやすいです。エンジニア向けには、トークン予算・履歴プロバイダー・MessageGroup の境界・before/after の実行タイミングを押さえる必要があります。
