Agent Framework の compaction 図解

結論: compaction は、長くなった会話履歴をそのまま全部モデルへ渡さず、重要な文脈を残しながら小さくする処理です。

この demo では src/agent/compaction.py で CompactionProvider を作り、DemoAgent の context_providers に登録しています。

なぜ必要か

上限超過

履歴が増えると、モデルのコンテキスト上限を超える可能性があります。

コスト増加

入力トークンが増えるほど、API コストも増えます。

応答遅延

モデルへ渡す入力が大きいほど、応答時間が長くなります。

TokenBudgetComposedStrategy の役割

複数の戦略を順番に実行します。推定トークン数が token_budget 以下になれば、そこで後続戦略を止めます。

各戦略の意味

戦略何をするか情報の残りやすさLLM が必要かこの demo での用途
ToolResultCompactionStrategy古いツール結果を短い要約メッセージにする高い不要最初に実行する軽い圧縮
SummarizationStrategy古い会話を LLM で要約する中程度必要長い会話の文脈を短く残す
SlidingWindowStrategy最新のメッセージグループだけ残す低い不要それでも長い場合の強めの制限
TruncationStrategy古いグループを削除する低い不要ad-hoc compaction の最終手段

メッセージグループ

Agent Framework の compaction は、単純に 1 メッセージずつ削るのではなく、関連メッセージをグループとして扱います。

flowchart TD
    S[system
常に保護される]
    U[user
ユーザー発話]
    A[assistant_text
通常の回答]
    T[tool_call
ツール呼び出し + ツール結果]
    Sum[summary
要約で作られたメッセージ]
tool_call は、ツール呼び出しとツール結果が対応しています。片方だけ削ると LLM API の入力として不整合になるため、まとめて扱います。

設定値の読み方

設定既定値意味
token_budget16_000before_strategy が目標にする推定トークン数
keep_last_tool_call_groups1最新いくつのツール呼び出しグループを完全な形で残すか
summary_target_count4要約後もそのまま残す最新メッセージ数
summary_threshold2要約を始めるまでの余裕値
keep_last_groups20最終的に残す最新の非 system グループ数
ad_hoc_max_n8_000ad-hoc 圧縮を始める推定トークン数
ad_hoc_compact_to4_000ad-hoc 圧縮後の目標推定トークン数

実装上の注意

トークン数は概算

CharacterEstimatorTokenizer は 4 文字を 1 トークン相当とみなします。モデル固有の正確なトークン数ではありません。

要約には LLM が必要

SummarizationStrategy は要約用 LLM クライアントが必要です。この demo では DemoApplication が haiku_client を渡しています。

TruncationStrategy は削除

TruncationStrategy は要約せずに古い情報を削除します。通常の会話では、先にツール結果圧縮と要約を使う構成が妥当です。
