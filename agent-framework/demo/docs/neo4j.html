Microsoft Agent Framework × Neo4j
拡張性 解説資料

GraphRAG + Memory

結論: Neo4j 統合は、Agent Framework に 「関係性をたどる知識検索」 と 「セッションをまたぐ永続メモリ」 を追加する拡張ポイントです。

GraphRAG は既存のナレッジグラフから回答根拠を取得するための拡張、Memory は会話からユーザー設定・事実・推論履歴を蓄積して再利用するための拡張です。両者を混同しないことが設計の入口です。

30秒で理解する
  • Neo4j GraphRAG: 既存のナレッジグラフを検索し、関連エンティティまでたどって回答の根拠を厚くする。
  • Neo4j Memory: 会話から記憶を抽出・保存し、次回以降の会話に自動で出せるようにする。
  • 拡張性の本質: Agent Framework の context_providers と tools に Neo4j を差し込み、検索・記憶・推論補助を外部化すること。

1Agent Framework に Neo4j を足すと何が広がるか

エージェントの「頭の外側」を拡張する

Agent Framework
ユーザー入力を受け、LLM とツールをオーケストレーション
→
Neo4j GraphRAG
既存知識を関係性込みで取得
+
Neo4j Memory

LLM のコンテキストだけに頼らず、知識と記憶を Neo4j 側に分離できます。

2GraphRAG と Memory の違い

Neo4j は Agent Framework 向けに2つの統合を提供しています。設計上は「既にある知識を探す」のか「会話から新しい記憶を作る」のかで分けます。

観点 Neo4j GraphRAG Neo4j Memory
目的 既存のナレッジグラフを検索し、回答を根拠付ける 対話から記憶を保存し、次回以降に呼び戻す
主な入口 Neo4jContextProvider Neo4jMicrosoftMemory、memory.context_provider、メモリツール
扱う情報 文書チャンク、エンティティ、関係、既存DB内の知識 会話履歴、ユーザー設定、事実、推論トレース、ツール利用パターン
検索の特徴 ベクター、フルテキスト、ハイブリッド検索と Cypher によるグラフトラバーサル 関連メモリの自動取得、明示的な記憶検索、エンティティ接続の探索
向く用途 社内文書、契約、設計情報、FAQ、関係性が重要な業務知識 ユーザー好み、顧客履歴、継続タスク、長期アシスタント
対応 Python と .NET の例が掲載 公式ページ上では Python タブの使用例が中心で、C# はまだ使用不可と記載

3Neo4j GraphRAG: 既存知識を「関係性込み」で検索する

普通のRAGで起きやすいこと

検索結果がテキストチャンク単位でバラバラに返る
関連する会社、人物、案件、文書のつながりが見えにくい
「この情報は何と関係しているか」を追加で推論しにくい

GraphRAG で広がること

関連エンティティまでグラフをたどれる
ベクター検索 + キーワード検索 + グラフ traversal を組み合わせられる
Cypher で返す文脈を細かく制御できる

GraphRAG の実行イメージ

質問
「Acme Corp のリスクは？」
→
検索
vector / fulltext / hybrid
→
Traversal
文書・会社・関係先をたどる
→
回答
関係性を含む根拠つき回答

Python 実装の要点

from agent_framework import Agent
from agent_framework.foundry import FoundryChatClient
from agent_framework_neo4j import Neo4jContextProvider, Neo4jSettings, AzureAISettings, AzureAIEmbedder

neo4j_settings = Neo4jSettings()
azure_settings = AzureAISettings()
embedder = AzureAIEmbedder(
    endpoint=azure_settings.inference_endpoint,
    credential=sync_credential,
    model=azure_settings.embedding_model,
)

neo4j_provider = Neo4jContextProvider(
    uri=neo4j_settings.uri,
    username=neo4j_settings.username,
    password=neo4j_settings.get_password(),
    index_name=neo4j_settings.vector_index_name,
    index_type="vector",
    embedder=embedder,
    top_k=5,
    retrieval_query="""
        MATCH (node)-[:FROM_DOCUMENT]->(doc:Document)
        OPTIONAL MATCH (doc)<-[:FILED]-(company:Company)
        RETURN node.text AS text, score, doc.title AS title, company.name AS company
        ORDER BY score DESC
    """,
)

agent = Agent(
    client=FoundryChatClient(...),
    instructions="You are a financial analyst assistant.",
    context_providers=[neo4j_provider],
)

4Neo4j Memory: 会話からグラフ型の記憶を作る

Memory は静的な知識ベース検索ではありません。会話の中からエンティティ、好み、事実、推論の流れを抽出し、Neo4j 上に接続された記憶として残します。

短期メモリ

会話履歴と最近のコンテキスト。今の会話を自然につなげるための記憶。

長期メモリ

ユーザー設定、事実、抽出されたエンティティ。セッションをまたいで再利用する記憶。

推論メモリ

過去の推論トレースやツール使用パターン。次回の判断や手順選択に使う記憶。

Memory の実行イメージ

会話
「飛行機は窓側が好き」
→
抽出
ユーザー設定・エンティティ
→
保存
Neo4j ナレッジグラフ
→
呼び戻し
次回の会話に自動で文脈提供

Python 実装の要点

from neo4j_agent_memory import MemoryClient, MemorySettings
from neo4j_agent_memory.integrations.microsoft_agent import (
    Neo4jMicrosoftMemory,
    create_memory_tools,
)

settings = MemorySettings(
    neo4j={
        "uri": os.environ["NEO4J_URI"],
        "username": os.environ.get("NEO4J_USERNAME", "neo4j"),
        "password": SecretStr(os.environ["NEO4J_PASSWORD"]),
    },
    embedding={"provider": "openai", "model": "text-embedding-3-small"},
)

memory_client = MemoryClient(settings)

async with memory_client:
    memory = Neo4jMicrosoftMemory.from_memory_client(
        memory_client=memory_client,
        session_id="user-123",
    )
    tools = create_memory_tools(memory)

    agent = Agent(
        client=FoundryChatClient(...),
        instructions="You are a helpful assistant with persistent memory.",
        tools=tools,
        context_providers=[memory.context_provider],
    )

5拡張アーキテクチャとしての整理

GraphRAG を入れる位置

回答前に、外部知識を検索してコンテキストとして追加します。

ユーザー質問
Neo4jContextProvider が関連サブグラフを取得
LLM が取得結果を使って回答

Memory を入れる位置

回答前に関連記憶を呼び戻し、回答後に新しい記憶を保存します。

会話開始
関連メモリを自動取得
会話後に新しいメモリを保存
設計上の重要点

GraphRAG と Memory は同じ Neo4j を使っていても、ライフサイクルが違います。GraphRAG は「既存知識を検索する処理」、Memory は「対話から知識グラフを育てる処理」です。運用ではデータ領域、権限、更新タイミング、削除ポリシーを分けて設計するのが安全です。

6どんな業務に向いているか

社内ナレッジ検索

部署、文書、案件、システム、担当者の関係をたどる。単なる全文検索より関係性を説明しやすい。

顧客対応エージェント

過去の会話、顧客の好み、問い合わせ履歴を記憶し、次回対応に反映する。

設計・障害調査

システム、ログ、変更履歴、依存関係をグラフ化し、原因候補のつながりを取得する。

営業・提案支援

会社、担当者、課題、過去提案、契約情報の関係を検索し、提案文脈を補強する。

パーソナルAI

ユーザーの嗜好、継続タスク、過去の意思決定を長期記憶として保持する。

FAQ高度化

FAQ、問い合わせ、カテゴリ、根拠文書、関連手順をつなげて、類似質問の回答品質を上げる。

7ベストプラクティス

GraphRAG と Memory を混ぜすぎない

検索対象の公式知識と、会話から生成される記憶は性質が違います。DB、ラベル、権限を分ける設計が無難です。

Cypher で返す文脈を絞る

関係をたどれるからといって全部返すとノイズになります。回答に必要な関係だけ返す retrieval_query を設計します。

メモリ保存にはポリシーを置く

何を記憶してよいか、いつ消すか、ユーザーにどう見せるかを決めます。特にPIIや機密情報は要注意です。

評価を分ける

GraphRAG は検索精度・根拠品質、Memory は想起精度・不要記憶の抑制・削除容易性で評価します。

8バッドプラクティス

Neo4j を入れれば精度が上がる、という考え方

Neo4j は関係性を扱う基盤です。グラフ構造、インデックス、Cypher、メモリ保存ルールが悪いと、むしろ不要な情報を拾って回答がぶれます。

会話メモリを無制限に保存する

Memory は便利ですが、記憶してはいけない情報まで保存するとリスクになります。保存対象、保持期間、削除方法、ユーザー確認の設計が必要です。

GraphRAG を通常RAGの完全上位互換として扱う

関係性が重要でない単純検索では、ベクター検索や全文検索だけで十分な場合があります。GraphRAG は「つながり」が価値になる場面で使います。

9採用判断フロー

  1. 既存の文書・DB・エンティティ関係を根拠として回答したい → GraphRAG を検討。
  2. 会話からユーザー設定や事実を学習し、次回以降も使いたい → Memory を検討。
  3. どちらも必要 → GraphRAG は公式知識、Memory はユーザー/会話由来の記憶として分離。
  4. 関係性が価値にならない → 通常RAGやシンプルな履歴管理で十分な可能性あり。
  5. 個人情報・機密情報を扱う → 保存ポリシー、削除ポリシー、監査ログを先に設計。
